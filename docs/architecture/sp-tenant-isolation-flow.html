Prism — Per-Tenant Isolation

How one embedded analytics app serves every client with its own identity and its own data — no Databricks logins.

Advito has ~130 client organizations. Prism embeds Databricks AI/BI dashboards and Genie chat for all of them from a single application, yet each client sees only its own travel data. The mechanism: every client organization is mapped to a dedicated Service Principal (SP), and every request runs as that SP. Unity Catalog enforces isolation at the data layer with a row filter, so the guarantee holds no matter what the app does. Clients authenticate through their own identity — they never touch a Databricks login.

System architecture

One application serves every client. The app resolves each request to a dedicated per-tenant Service Principal and runs as it; Unity Catalog enforces the data boundary.

Acts as the tenant Service Principal Hosting / platform component

Request flow — login to scoped data

A single request, end to end. Every hop after login carries the tenant identity, and the last two hops make the isolation impossible for the app to bypass.

1

White-label login

A client user — alice@acmetravel.com — signs in through Prism's branded login (or the client's own IdP). No Databricks account, no Databricks UI.

2

Edge session carries the tenant

The edge gateway mints a signed session cookie holding the user's tenant_id — e.g. acme-travel — and reverse-proxies to the app. This tenant_id is the single join key for everything downstream.

3

Tenant registry resolves the Service Principal

The app looks up tenant_id in apex_client_registry (Lakebase) and gets that tenant's dedicated sp_app_id and Genie space. The SP's OAuth secret is stored AES-GCM encrypted in apex_sp_credentials.

4

Mint a token — as the tenant SP

The app decrypts the secret and mints a short-lived M2M OAuth token (client_credentials) for that SP. Nothing is provisioned per user; identity is per client organization.

5

Every downstream call runs as that SP

The token drives all three embedded surfaces. Because the SQL caller identity (session_user()) is the tenant SP, the data layer can enforce scope on its own — the app cannot accidentally leak across tenants.

Genieas SP

Natural-language Q&A over the tenant's data, via the Genie API.

AI/BI Dashboardas SP

Embedded dashboard token minted for the tenant SP.

SQL / Warehouseas SP

Ad-hoc queries execute under the SP identity.

6

Unity Catalog row filter — the enforcement point

The governed fact table summarydataset has a row filter attached on client_id. The filter joins a mapping table on the caller's SP identity, so a tenant SP only ever sees its own rows. A mapping row of '*' (the app's own SP) is a wildcard used for the operator "see-all" view and the onboarding picker.

-- attached to summarydataset ON (client_id)
CREATE OR REPLACE FUNCTION tenant_row_filter(tenant_id STRING)
RETURN
  is_account_group_member('admins')          -- back-office bypass
  OR EXISTS (
    SELECT 1 FROM sp_tenant_mapping m
    WHERE m.sp_app_id = session_user()      -- = the tenant SP
      AND m.active = true
      AND (m.tenant_id = tenant_row_filter.tenant_id
           OR m.tenant_id = '*')          -- '*' = see all (operator)
  )

Verified live: each tenant SP returns only its own client_id; the app SP (mapped to '*') returns all clients.

Sequence — a request over time

The same request as message exchanges between participants. The two accent hops — minting the token and the Unity Catalog row-filter evaluation — are where the per-tenant guarantee is established and enforced.

Management plane — the operator console

Onboarding a client is one operator action. It creates the SP, mints and encrypts its secret, registers the tenant, writes the sp_tenant_mapping row, and grants the SP access to the dashboards, Genie space, and governed table — then every step is audited.

OnboardCreate SP + secret → register → map → grant. Secret shown once.
RotateMint a fresh secret and revoke all previous ones.
DeactivateDisable the SP, drop its secret, flip the mapping off.
ReactivateRe-enable the SP with a new secret.
DeleteTear down the SP and remove all registry + mapping rows.
VerifyQuery as each SP and assert it sees only its own rows.

Key code

The load-bearing pieces, straight from the app.

1 · Onboard a tenant — create the Service Principalserver/tenants/sp_lifecycle.py
def onboard_sp(tenant_id, display_name, genie_space_id=None):
    w = runtime.admin_client()                  # workspace-admin client
    display = f"{TENANT_SP_PREFIX}-{tenant_id}"  # e.g. prism-tenant-acme-travel

    sp = w.service_principals.create(display_name=display, active=True)
    sp_app_id = sp.application_id

    # mint the SP's OAuth secret (returned exactly once)
    created = w.service_principal_secrets_proxy.create(service_principal_id=sp.id)
    secret  = created.secret

    registry.insert_tenant(tenant_id=tenant_id, sp_app_id=sp_app_id,
                           sp_display_name=display, genie_space_id=genie_space_id)
    registry.put_secret(sp_app_id, secret)       # AES-GCM encrypted at rest
    return {"sp_app_id": sp_app_id, "client_secret": secret}

3 · Row-level security — filter, attach, mapapply_row_filter.py · unity_catalog.py
-- the row filter: keyed on the SQL caller identity (the SP)
CREATE OR REPLACE FUNCTION tenant_row_filter(tenant_id STRING)
RETURN is_account_group_member('admins')
    OR EXISTS (SELECT 1 FROM sp_tenant_mapping m
               WHERE m.sp_app_id = session_user() AND m.active
                 AND (m.tenant_id = tenant_row_filter.tenant_id OR m.tenant_id = '*'));

-- attach it to the governed fact table (once)
ALTER TABLE prism_travel.summarydataset
  SET ROW FILTER prism_travel.tenant_row_filter ON (client_id);

-- one mapping row per onboarded tenant SP
INSERT INTO sp_tenant_mapping (sp_app_id, tenant_id, active)
VALUES ('<sp_app_id>', '<tenant_id>', true);
4 · Prove it — verify isolation as the SPserver/tenants/unity_catalog.py
# query the governed table AS the tenant SP and assert what it can see
token = minter().get_token(sp_app_id, secret_for_sp(sp_app_id))
seen  = run_sql_as(token, "SELECT DISTINCT client_id FROM summarydataset")
